# 29 — AI Phase Roadmap (3 agents per phase: a / b / c)

> Place at `CityCart/docs/29-ai-phase-roadmap.md`.
> This file is the **build order**. It replaces section 7 of doc 27 and the phase columns in doc 27's tables.
> Architecture, guardrails and file layout stay in `27-ai-agents-and-automation-plan.md`. Vision details stay in `28-sightwise-integration.md`.

## How to work through it

1. Each phase contains **three** sub-phases (`1a`, `1b`, `1c`). Build and finish them **one at a time**: endpoint + tools + UI + tests, then move on.
2. One branch per sub-phase, for example `feature/ai-1a-listing-writer`, merged when its "Done when" is true.
3. A phase is **complete** only when its **gate** (below) passes. Then tag it (`ai-phase-1`) and start the next phase.
4. Order: **Phase 0 (foundation) -> Phases 1-4 (agents) -> Phase 5 (automation) -> Phase 6 (vision) -> Phase 7 (hardening)**.

## Overview

| Phase | Theme | a | b | c |
|---|---|---|---|---|
| 0 | Foundation | provider router | usage log + cache + kill switch | route, auth, rate limit |
| 1 | Quick-win generation | Listing writer (brand) | Review summarizer (customer) | Chat translator (customer + brand) |
| 2 | Customer assistants | Shopping assistant | Order helper | Service booking helper |
| 3 | Seller intelligence | Seller advisor (restock, pricing, analytics Q&A) | Catalogue matcher + CSV cleaner | Reply drafter (reviews + chat) |
| 4 | Operations agents | Picker substitution | Admin triage (billing help, support) | Moderation agent |
| 5 | **Automation** | Event automations (review, product) | Scheduled automations (nightly, weekly) | Risk and admin automations |
| 6 | **Vision link** (Sightwise) | "Scan product" in listing form | Fruit freshness scan | Return evidence + authenticity |
| 7 | Hardening | Security tests | Quota and cost review | Docs, release |

## Phase 1 — Quick-win generation (low risk, no tools, no data access)

### 1a — Listing writer (Brand)
- **What:** from a few words of notes, drafts title, description and a suggested category. Image input is deferred to the Phase 6 vision link.
- **Endpoint:** `POST /api/v1/ai/listing-draft` (role: BRAND_ADMIN or BRAND_EMPLOYEE). Body `{ notes }`, 3–400 characters.
- **Tools:** none. The server loads the active leaf categories itself, then validates the model output with zod `{ title, description, category }` and resolves the category against that list (`null` when it matches nothing). Nothing is written to the database.
- **UI:** "Draft the details for me" panel in the brand's **Request a new product** form on Add product (client). Brands do not author a listing's name, description or category directly — those come from the catalogue — so the request form is the only place a brand writes new product copy. On success the panel fills name, description and category; the brand edits them before sending the normal catalogue request. The panel is hidden when `AI_ENABLED` answers 503.
- **Tests:** zod validation (too short/too long); non-brand role gets 403 without a provider call; notes are sanitized; category resolved by id or name; unknown category returns `null`; malformed model output returns 502 `AI_BAD_OUTPUT`; provider failure returns 503; kill switch and daily limit return before any provider call; brand-employee membership path works.
- **Done when:** the button fills the form in a real brand account and the AI label is visible.

### 1b — Review summarizer (Customer-facing)
- **What:** 2-3 line summary of pros/cons for a product.
- **Endpoint:** `GET /api/v1/ai/products/:id/review-summary` (signed-in, any role). Guests keep the normal reviews and simply do not see the card.
- **Tools:** reads that product's approved reviews only (inside the service, no model-controlled IDs). The product must be public: active listing in an active brand. Review text is sanitized and marked as data in the prompt.
- **Cache:** `AiCache` keyed by product + approved review count for one hour; regenerate only when count changes. Minimum 3 approved reviews, below which the endpoint answers `summary: null` without a provider call.
- **UI:** "AI summary" card above the reviews grid on the product page (client). It is fetched only for signed-in users with 3+ reviews and disappears silently on a kill switch, quota or bad output. Shopper app is deferred with the "web first, apps later" decision.
- **Tests:** cache hit avoids a provider call; review text containing instructions is sanitized and never treated as instructions; below 3 reviews no provider call; a changed count regenerates; non-public product 404; malformed output 502; provider failure 503; kill switch and daily limit return before any provider call.
- **Done when:** summary appears, is cached, and refreshes after a new review.

### 1c — Chat translator (Customer + Brand)
- **What:** translates one chat message on request (Urdu / English / Roman Urdu).
- **Endpoint:** `POST /api/v1/ai/translate` with `{ messageId, targetLang }`; `targetLang` is `en`, `ur` or `roman-ur`.
- **Rule:** the caller never sends the text. The server loads the message and its conversation and checks the signed-in user is that conversation's customer or brand. The message body is sanitized and marked as data in the prompt; the model must answer `{ translation }`, validated with zod.
- **Roles and scope:** `CUSTOMER`, `BRAND_ADMIN`, `BRAND_EMPLOYEE` (employee needs `messages.view`), through `chatAccess`. Store chats only in this sub-phase; the direct provider and booking threads stay without Translate.
- **Cache:** `AiCache` keyed by `(messageId, lang)` for 7 days, because messages are immutable.
- **UI:** "Translate" action under a message bubble in the web ChatPanel (customer and brand dashboards). The picker offers English / اردو / Roman Urdu; the translation appears in an AI-labelled card **under** the original, which stays visible.
- **Tests:** non-participant gets 403; another brand gets 403; a non-chat role is refused before the message is loaded; invalid language 400; malformed id and missing message 404; cache hit avoids a provider call; cached by `(messageId, lang)`; injected instructions are stripped but the text survives; malformed output 502; provider failure 503; kill switch and daily limit return before any provider call.
- **Note:** a non-participant gets **403 `NOT_A_PARTICIPANT`** (the roadmap's required answer) rather than the chat service's deliberate 404 anti-probing answer. That is intentional for this endpoint and documented in docs/05 §23a.
- **Done when:** both sides can translate a message and the original stays visible.

**Gate 1:** 1a + 1b + 1c done, tests green, `AiUsage` reviewed (calls per agent, failure rate), kill switch tested again. Tag `ai-phase-1`.

## Phase 2 — Customer assistants (first use of tools)

Before 2a: build the **tool layer** (`tools/*.tool.js`, read-only, `(ctx, args)`) and the **agent loop** (max 3 steps, zod-validated tool calls). This is the main work of 2a.

### 2a — Shopping assistant
- **What:** "cheap rice near me", "gift under 3000", in Urdu / English / Roman Urdu.
- **Endpoint:** `POST /api/v1/ai/shop-assistant`.
- **Tools:** product search, categories, discover/nearby (existing services).
- **Output:** short answer + **product cards from real DB results**; the model may not invent products.
- **UI:** chat widget in the client and shopper app; tapping a card opens the normal product page.
- **Tests:** answers only reference returned product IDs; injection text in a product description is not obeyed; fallback to plain search on AI failure.
- **Done when:** five scripted queries return correct real products.

### 2b — Order helper
- **What:** "where is my order?", explains status, cancellation and return rules.
- **Endpoint:** `POST /api/v1/ai/order-helper`.
- **Tools:** the caller's own orders (`ctx.userId` only), return/cancel policy text from settings.
- **Rule:** can *suggest* **View order** and **Cancel order** buttons; the user performs the action on the normal order page. Cancel is offered only for an unpaid `PENDING` order, the rule the backend enforces. There is **no "Start return"** button: v2 has no customer-initiated return after delivery (docs/22 §F), so the answer explains the door-return rule instead.
- **Tests:** **user A can never read user B's order** (explicit test); unknown order returns a polite "not found".
- **Done when:** correct status answers for orders in each state.

### 2c — Service booking helper
- **What:** finds a suitable service provider and suggests a time slot.
- **Endpoint:** `POST /api/v1/ai/service-helper`.
- **Tools:** service discovery, categories, availability.
- **Rule:** only suggests; booking goes through the existing booking flow.
- **Tests:** suggested slots exist in availability data; no double-booking suggestions.
- **Done when:** a request like "AC repair tomorrow evening" returns real providers and slots.

### 2d — Recipe shopping list
- **What:** "chicken biryani for 6" -> the dish's ingredients, each matched to a real product nearby.
- **Endpoint:** `POST /api/v1/ai/recipe-list`.
- **Tools:** product search only (read-only).
- **Rule:** the model **extracts ingredients only**; matching is ordinary code over the same public product search the Stores page uses, so no product, price or shop can be invented. The list is a draft the customer edits; adding it to the cart goes through the normal cart API. Merged rows cannot add the same product twice.
- **Tests:** injected text is treated as data; unmatched ingredients stay honest ("Not found nearby"); provider failure degrades to a plain product search; extraction is cached, matching is live.
- **Done when:** a scripted recipe returns real products for most ingredients and the customer can add them to the cart in one click.

### 2e — Product comparison
- **What:** "compare two rice packs" -> a side-by-side table of real listings: price, stock, rating and the listing's own attributes.
- **Endpoint:** `POST /api/v1/ai/compare`.
- **Tools:** `compare_products { query, limit? }` — the same public product search the shopping assistant uses, enriched by ordinary code with up to 8 attribute pairs and approved-review ratings.
- **Rule:** the model **chooses which returned ids to show, at most 3**; every cell is read by the server from the listing, so no price, attribute or rating can be invented. The card is read-only; ordering happens on the normal product page. The product page's "Compare with similar products" button opens the panel with a prefilled question and never sends it.
- **UI:** **Compare** mode in the web `Ask CityCart` panel and a `CompareCard` table (attribute rows are the union of the shown products' keys, capped at 8).
- **Tests:** invented ids are dropped; strict tool arguments reject an ownership field; catalogue text stays data; the 3-step guard and provider failure both degrade to a plain product search; kill switch and non-customer role return before any provider call.
- **Done when:** a scripted comparison returns 2–3 real listings with attribute rows and the table renders in the panel.

### 2f — Chat reply draft (customer)
- **What:** a customer types what they want to say ("ask when they can come") and gets a ready-to-send message in the chat composer.
- **Endpoint:** `POST /api/v1/ai/chat-draft` with `{ kind, id, intent }`; `kind` is `provider` (direct chat) or `booking` (booking chat, `id` is the booking id). `intent` is 3–300 characters.
- **Rule:** the server loads the thread itself and checks the signed-in customer is its customer; another customer's thread is **404**. Only the last 8 messages reach the prompt, `SYSTEM` messages are dropped, attachments become `[sent a photo]`, and each message is cut to 500 characters and marked as data. A closed booking chat answers **409 `CHAT_NOT_OPEN`** before any provider call. The model answers `{ draft }` only (≤1000 characters) and nothing is written to the database.
- **Tools:** none; the endpoint reads the caller's own thread and calls the model once.
- **UI:** "Draft with AI" in the web `ChatPanel` composer on direct provider and booking threads; the draft fills the message box and is never auto-sent. Store chat keeps Translate and has no draft.
- **Tests:** non-customer role refused before the thread is loaded; another customer's provider and booking threads both 404; unknown or malformed id 404; closed booking 409; the prompt carries the provider name, recent history and intent in order and says the data is not instructions; injected text is sanitized; an empty thread is honest; malformed or oversize drafts 502; provider failure 503; kill switch and daily limit return before the thread is loaded.
- **Done when:** the button fills the composer in a real provider and booking thread and the customer can edit and send.

### 2g — One chat instead of mode buttons
- **What:** the customer no longer picks Find products / Compare / Cook / My orders / Services before typing. One `Ask CityCart` chat accepts any question and shows capability hints in the bot.
- **Endpoint:** `POST /api/v1/ai/chat` with `{ message, cityId?, lat?, lng?, lastMode? }`. `lastMode` is only a hint for short follow-ups and is validated; the server always routes.
- **Routing:** deterministic and testable (docs/05 "Unified customer chat"): order, then comparison, then recipe, then service, otherwise shopping. Greetings and `help` answer with hints and **do not** call a provider.
- **Rule:** the unified route calls the existing agents unchanged, so every card and every scope is still produced by the same read-only tools. The response adds `mode` and `hints`; the old per-agent endpoints stay available for the app and deep links.
- **UI:** the five mode pills are replaced by one hint list (Products, Orders, Services, Recipe list, Compare) and every example goes to `/ai/chat`. Answers are labelled with the mode that produced them; help answers render their hint chips. The product page's compare button only prefills the question.
- **Tests:** classifier cases in English, Urdu and Roman Urdu; precedence; follow-ups with `lastMode`; a client-sent mode cannot choose the agent; help spends no provider call; auth, role, validation, kill switch and daily-limit checks; duplicate product ids collapse; a tool+answer decision still runs the tool; service prices reach the model in rupees, not paisa.
- **Done when:** a mixed scripted conversation (product → order → service → recipe → compare) works in one thread with the right cards.

**Gate 2:** 2a + 2b + 2c + 2d + 2e + 2f + 2g done, cross-tenant/cross-user tests pass, injection tests pass. Tag `ai-phase-2`.

## Phase 3 — Seller intelligence (brand side)

### 3a — Seller advisor
- **What:** "what should I restock?", "why did sales drop this week?", pricing suggestions.
- **Endpoint:** `POST /api/v1/ai/seller-advisor` (brand roles).
- **Tools:** analytics and inventory for `ctx.brandId` only. Numbers are computed by your code and passed in; the model explains, it does not calculate.
- **UI:** advisor panel in the brand dashboard and business app.
- **Tests:** a brand can never see another brand's numbers; numbers in the answer match the tool output.
- **Done when:** restock answer lists real low-stock items from that brand's data.

### 3b — Catalogue matcher + CSV cleaner
- **What:** (1) on a new product, suggests an existing global-catalogue match and flags likely duplicates; (2) cleans messy CSV rows (names, units, categories) with preview-then-apply.
- **Endpoints:** `POST /api/v1/ai/catalogue-match`, `POST /api/v1/ai/csv-clean`.
- **Tools:** catalogue search (read-only).
- **Rule:** CSV cleaner returns a **diff preview**; nothing is written until the brand confirms.
- **Tests:** diff shape; confirm step required; large CSV is processed in chunks.
- **Done when:** a messy 50-row CSV produces a correct preview and a clean import after confirmation.
- **Status:** both halves are built on `new`. 3b-1 (2026-11-21) — `catalogue.tools.js` (the two reads and the match arithmetic), `catalogueMatch.agent.js`, `POST /ai/catalogue-match` behind `products.create`, the panel in the request form, and `tests/ai/catalogueMatch.test.js` (46 cases: the arithmetic, what each read may see, every role, an injected `brandId`, escaped input, invented ids, degraded answers, kill switch and daily limit). 3b-2 (2026-11-21) — `csvClean.rules.js` (the deterministic text fixes, read through the importer's own column map and row limit), `csvClean.prompt.js`, `csvClean.agent.js` (catalogue resolution, bounded chunks, verified suggestions only), `POST /ai/csv-clean` behind `products.create` **and** `products.update` with the file as the body, the **Clean it up first** diff table in the import dialog, and `tests/ai/csvClean.test.js` (109 cases: every rule and every cell it refuses to touch, ragged rows left alone, the importer's refusals, chunking at 20 rows per call and 60 per file, an invented line number dropped, a suggestion no catalogue item answers kept as a hint, markup stripped, nothing written, another shop's private item never resolved, and a messy file that the importer refuses becoming one it accepts).

### 3c — Reply drafter (reviews + chat)
- **What:** drafts a polite reply to a review or a customer chat message.
- **Endpoints:** `POST /api/v1/ai/reply-draft` with `{ type: 'review'|'chat', id }`.
- **Rule:** returns a draft only; the brand edits and sends through the normal path. Never auto-sends.
- **Tests:** ownership check on the review/chat; draft never sent without a user action.
- **Done when:** draft appears in the reply box and sending uses the existing endpoint.
- **Status:** built on `new` (2026-11-21). `replyDraft.prompt.js`, `replyDraft.agent.js`, `POST /api/v1/ai/reply-draft` behind `products.view` for a review and `messages.manage` for a thread (one route, the permission the `type` needs), the **Draft a reply** button in the brand Messages composer and on each Reviews card, and `tests/ai/replyDraft.test.js` (68 cases: the exact tenant filter on every read, another shop's review and thread answered 404 before any provider call, a hidden unapproved review answered 404, an unapproved/inactive membership refused, every role, an injected `brandId`/`customerId`/`history` ignored, no price, stock, order status, e-mail or phone ever leaving the server, the customer's own text held as data, the 10-message window, markup stripped, `NOTHING_TO_ANSWER` on a shop-only thread, no write method called for either half, and the kill switch, daily limit and `AI_BAD_OUTPUT` paths).
- **Open gap for the owner:** the review half cannot yet be *sent*, because a `Review` has no reply field and no publish endpoint anywhere in the API. The roadmap's "sending uses the existing endpoint" holds for chat (`POST /chats/:id/messages`) and not for reviews, so the reviews UI shows the draft with a Copy button and says plainly that CityCart does not post shop replies on reviews. Adding a public review reply is a product decision — a new field, an endpoint, moderation and a customer-facing surface — and was not invented here.

### 3d — Suggested additions (owner-approved backlog, 2026-11-21)

These came out of the two "what else can the brand side do with AI" reviews (the second half of the list was added on 2026-11-21 so nothing lives only in a conversation). They all follow 3a's rule exactly: **the server computes every number, the model only explains and chooses which of the shop's own products to show.** None of them writes to the database without a human clicking the normal button, and none of them reads another brand's data.

| Sub | Feature | Endpoint | What it answers | Built first? |
|---|---|---|---|---|
| 3d-1 | Returns reason clusterer | `POST /api/v1/ai/returns-insights` | "why do people send this back?" — groups **this shop's** returned lines by the four stored reasons (`DAMAGED`, `WRONG_ITEM`, `NOT_WANTED`, `MISSING`), counts them per product, states the value lost from `returnedSubtotal` / `refundAmount`, and names the likely cause ("size runs small on 3 of 4"). It also drafts the wording of the fix and of a dispute reply for the brand to send itself | **built — 2026-11-21 (see 3e)** |
| 3d-2 | Restock calendar | `POST /api/v1/ai/restock-calendar` | "what should I have bought last week?" — the shop's own delivered orders grouped by week-of-year, so a festival or month-end rush that sold out before is flagged before it happens again | **built — 2026-11-21 (see 3f)** |
| 3d-3 | Listing quality score | `POST /api/v1/ai/listing-quality` | "why is this page not selling?" — scores a listing on the fields it is missing (description length, attributes, image count, price vs `compareAtPrice`, stock) and lists the fixes in order; a score, never a verdict | **built — 2026-11-21 (see 3g)** |
| 3d-4 | Weekly shop report | `POST /api/v1/ai/shop-report` | "how did the shop do this week?" — one plain-language paragraph plus the three products that moved, from the same `getBrandAnalytics` numbers the dashboard charts use, so the text and the charts can never disagree | **built — 2026-11-21 (see 3h)** |
| 3d-5 | Delivery performance | `POST /api/v1/ai/promise-check` | "am I over-promising, and where did today go wrong?" — each branch's quoted window against this shop's own completed orders, its on-time rate, and the reason behind a bad day from the shop's own delivery records. Shown on the brand delivery surfaces | no |
| 3d-6 | COD payout explainer | `POST /api/v1/ai/payout-explain` | "why is this payout not the order total?" — walks one payout line by line (COD collected, refunds, fee refunds, adjustments, commission) using the numbers the cash and billing records already carry, so a brand admin reads the difference instead of asking support. Every amount is already stored; the model never recalculates | no |
| 3d-7 | Deadstock re-pricing | `POST /api/v1/ai/deadstock-pricing` | "what is sitting and what should it cost?" — listings with zero sales for N days, a suggested markdown and the margin impact computed server-side from the listing's own `price`, `compareAtPrice` and cost. Pairs with 3a's stock alerts, and **never** uses another shop's prices | no |
| 3d-8 | Existing-listing photo pass | `POST /api/v1/ai/photo-review` | "which of my live photos should change?" — alt text and a better first image for products that are already listed, not only new ones. Depends on Sightwise being deployed, so it is last and belongs to Phase 6 as much as here | no |

**Rules that apply to all eight:** brand roles only, `requireTenant` + the permission the existing surface for that data already uses (`3d-1` and `3d-5` sit on `delivery.view`, the same guard as `GET /returns` and the brand delivery screens — **not** `orders.view`), `AI_ENABLED` kill switch and the daily limit ahead of any provider call, rupees spelled as rupees, `null` instead of a fabricated comparison when there is no baseline, and every product name, reason or payout line from the database is marked as data in the prompt, never as an instruction. 3d-6 and 3d-7 touch money, so the arithmetic stays in `services/` and a test asserts the answer's numbers equal the records' numbers. 3d-8 is the only one that needs a second system: it waits for Phase 6a.

### 3e — Returns reason clusterer (the first of 3d, built in the first half)
- **What:** the brand asks why orders come back and gets the real reasons, grouped, with counts and the products they cluster on, plus the rupee value of what came back.
- **Endpoint:** `POST /api/v1/ai/returns-insights` (brand roles, `delivery.view` + `requireTenant` — the same guards as `GET /returns`, because it answers the same inbox).
- **Tools:** this brand's `Return` rows only — the four stored reason enums, the per-line `productName`, `quantity`, `restock`, and `returnedSubtotal` / `refundAmount` / `feeRefunded` — plus the delivered order and listing behind them. Counts, percentages and totals are computed in code; the reason enum is never free text, so a theme is always one of the four.
- **UI:** a panel on the brand Returns page for the whole shop, and on `ReturnDetail.jsx` a drafted dispute/decision reply for that one return — copy only, since the store's real action stays the ordinary **Mark received** / restock-decision buttons.
- **Rule:** the model may re-word a reason for clarity, may not invent a reason that is not in the rows it was given, and never changes a return, refund, restock or order state.
- **Tests:** a brand never sees another brand's returns; a reason-shaped instruction stays marked as data; counts in the answer equal the counts in the rows; kill switch and daily limit return before a provider call.
- **Done when:** a scripted set of returns answers with the top themes, their counts and the real product names.
- **Status:** built on `new` (2026-11-21). `returnsStats.rules.js` holds every count (reason totals, per-product patterns, shares, shop-fault split, restocked against written off, and `returnedSubtotal` read straight off the records — the same field and addition `GET /returns/summary` uses, over the window asked for, so the panel is the inbox's own arithmetic and never a second version of it); `returnsInsights.prompt.js` + `returnsInsights.agent.js` read only `Return` rows scoped to `ctx.brandId` and the requested window, and `POST /api/v1/ai/returns-insights` sits behind `delivery.view` + `requireTenant` like the inbox it explains. The panel is on `pages/brand/Returns.jsx` (`components/brand/ReturnsInsights.jsx`) and the single-return reply is on `pages/brand/ReturnDetail.jsx` (`components/brand/ReturnReplyDraft.jsx`); both hide themselves when `/ai/ping` answers 503 or the caller lacks `delivery.view`. `tests/ai/returnsInsights.test.js` covers it in 69 cases.
- **Two rules the tests hold:** a theme naming a reason this shop's own counts do not contain is dropped before the answer is sent, and a product that appeared twice inside one refusal counts as one return — the same refusal is not two patterns. A return whose lines carry no reason the enum knows contributes nothing at all, not even its money.

### 3f — Restock calendar (the second of 3d)
- **What:** the shop asks what it should have bought last week and gets its own selling rate week by week, the stock that covers it, and the rush weeks that already caught it out once.
- **Endpoint:** `POST /api/v1/ai/restock-calendar` (brand roles, `analytics.view` + `requireTenant` — the same guard as the dashboard charts it explains).
- **Tools:** one `$facet` aggregation over this brand's `DELIVERED` orders (units per product per week, units shop-wide per week, a count of delivered orders that never unwinds line items) plus one `Inventory` read for the top-selling SKUs only, selecting `quantity`, `reservedQuantity`, `lowStockThreshold`, `trackInventory`.
- **UI:** the **AI restock read** panel at the foot of `pages/brand/Overview.jsx` (`components/brand/RestockCalendar.jsx`) — window chips, the week bars, the ranked product rows with their attention badge, the model's notes on a row and its checks-the-shop-can-do-itself list. It hides itself when `/ai/ping` answers 503 or the caller lacks `analytics.view`.
- **Rule:** every week, average, percentage, cover and suggested-unit count is worked out in `restockCalendar.rules.js` and tested there; no money field is read at all, the prompt is told it may not calculate, may not name a festival as fact and may not guess a supplier lead time. Nothing is created, ordered, restocked, reserved, adjusted or scheduled.
- **Tests:** a brand never sees another brand's units; the week in progress is excluded from every figure; a pending/cancelled/rejected order buys nothing; a renamed listing is shown with its current name and its markup stripped; invented or off-table `watch` ids are dropped; a large catalogue is measured over a bounded set and says so.
- **Done when:** a scripted four-week history answers with the right week bars, the right ranked rows and no number the rows do not support.
- **Status:** built on `new` (2026-11-21). `restockCalendar.rules.js` holds the window (whole Monday-to-Monday weeks, 4–13, current part-week left out), the bucketing, `availableQuantity = quantity - reservedQuantity` exactly as analytics and the stock alerts read it, cover at the product's own weekly rate, `suggestedUnits` to fill a fortnight, spike against the earlier weeks (`null` when there is no baseline, never a fabricated 0%), the passed-rush flag, the one-attention filing and the tier-first ranking; `restockCalendar.prompt.js` hands the model those figures as data and `restockCalendar.agent.js` scopes both reads to `ctx.brandId` and returns the counts whether or not the provider answers. `tests/ai/restockCalendar.test.js` covers it in 93 cases.
- **Two rules the tests hold:** the `totals` count *facts*, not the single tier each row was filed under — a product that is both short of stock and jumping is counted in both lines, because "0 products jumped" next to a row that jumped 200% is a lie a ranking rule would tell. And the panel's table is literally `stats.shown`, the same array the prompt is printed from, so the text can never be explaining a different list from the one the shop reads.

### 3g — Listing quality score (the third of 3d)
- **What:** the shop asks why one of its live pages is not selling and gets the listing read out field by field — words, photos, details, price pair, stock — as a score out of 100 and the gaps ranked by how many points each one is worth.
- **Endpoint:** `POST /api/v1/ai/listing-quality` (brand roles, `products.view` + `requireTenant` — the same guard as the product page it sits on, because it explains a listing the caller is already allowed to read).
- **Tools:** exactly two reads, both filtered by `brandId` in the query itself: one `Product` (`name description images attributes price compareAtPrice sku status isActive`) and one `Inventory` (`quantity reservedQuantity lowStockThreshold trackInventory`). Photo URLs are counted, never sent.
- **UI:** the **AI listing check** card at the foot of `pages/brand/ProductForm.jsx` (`components/brand/ListingQuality.jsx`), edit mode only — a listing that has never been saved has nothing to score. Score bar, the visibility line, the per-field rows with their points and facts, and the model's instruction under each gap. It hides itself when `/ai/ping` answers 503 or the caller lacks `products.view`.
- **Rule:** weights and bands live in `listingQuality.rules.js` and sum to exactly 100; the prompt is told it may not re-score, may not promise a result and may not suggest a price (that is 3d-7's job, and it needs its own approval). Nothing is written — the listing keeps its old fields until the shop saves the ordinary form.
- **Tests:** another shop's id and a missing id 404 identically; injected `brandId`/`score`/`price`/`inventory` in the body are ignored; a `compareAtPrice` below the price scores 0 as a discount that does not exist while a listing with no compare-at takes full marks; a fix naming a field with no gap is dropped; the daily limit and the kill switch answer before either read runs; no write method on `Product` or `Inventory` is ever called.
- **Done when:** a scripted listing answers with the score the checklist adds up to, in the order the checklist ranked it, and the same numbers appear with the provider switched off.
- **Status:** built on `new` (2026-11-21). `listingQuality.rules.js` holds the seven weighted checks and their bands, `visibilityOf` and the gap-ordered `fixes`; `listingQuality.prompt.js` prints those figures as data and `listingQuality.agent.js` scopes both reads to `ctx.brandId`, filters the model's fixes to the server's own gaps and returns the score whether or not the provider answers. `tests/ai/listingQuality.test.js` covers it in 90 cases.
- **Two rules the tests hold:** `visibility` is reported but **not scored** — a draft is an unfinished listing, not a bad one, and charging for it would push a shop to publish half-written copy. And `Number(null)` is 0: a listing with no compare-at price is not a listing priced at nothing, so the absence is read before the number, and the fake-discount zero fires only when a strike-through price is really below the price.

### 3h — Weekly shop report (the fourth of 3d)
- **What:** the shop asks how the week went and gets one paragraph in its own language, the three listings that moved most, the day that earned best, the share of orders it could not deliver and the short-stock lines it could still top up — all beside the dashboard charts it is already reading.
- **Endpoint:** `POST /api/v1/ai/shop-report` (brand roles, `analytics.view` + `requireTenant` — the same guard as the dashboard it explains). `days` is an integer from 7 to 30 (the panel offers 7, 14 and 30) and `from`/`to` cannot be sent, because a caller must not aim a report at a week it did not ask for.
- **Tools:** three reads and all of them the dashboard's own — `getBrandAnalytics` over the current window, the same call over the equal window before it, and one `soldByProduct` units aggregate for the previous window limited to the listings that sold now. The agent reads no `Product`, `Inventory` or `Delivery` row itself, so a report cannot be a second, different calculation of a number the charts already show.
- **UI:** the **AI week read** card above the restock panel at the foot of `pages/brand/Overview.jsx` (`components/brand/ShopReport.jsx`) — window chips, the three like-for-like columns, the whole-window tiles, the ranked mover rows with the model's note under each, the short-stock list and the checks-the-shop-can-do-itself list. It hides itself when `/ai/ping` answers 503 or the caller lacks `analytics.view`.
- **Rule:** every sum, average, offset pairing, share and percentage is worked out in `shopReport.rules.js`; money is rounded to whole rupees before the prompt is written and the model is told it may not add, subtract, average, re-rank, estimate, blame the shop for a part-day or suggest a price, a discount or a margin. Nothing is stored, mailed, scheduled or posted — the only record the call makes is its `AiUsage` row.
- **Tests:** another shop's id in the body is ignored and its orders never reach a figure; a `customerId`, order number or phone is kept out of the trimmed payload and out of the provider body; every product id in the answer is one this shop owns; a listing title that tries to give an instruction reaches the prompt flattened, stripped of markup and marked as data; a `days` of 0, 6, 31, 2.5, `"seven"` or `true` is refused rather than widened; an invented or off-list `note` product is dropped, one note per product, at most three; the kill switch and the daily limit answer before a single order is read; no write method on `Order`, `Product`, `Inventory` or `Delivery` is ever called. `tests/ai/shopReport.test.js` covers it in 130 cases.
- **Two rules the tests hold:** the day still running is dropped from **both** windows, so the like-for-like columns are the same weekdays and a shop that is only nine hours into Saturday is not told it declined; and an empty week costs no AI request at all — `empty: true`, the zeroed counts, `insight: null`, `degraded: false`, because there was nothing to compare and so nothing worth sending.
- **Done when:** a scripted two-week history answers with the paragraph, the movers and the comparison the order rows themselves support, and the same figures appear with the provider switched off.

**Gate 3:** 3a + 3b + 3c + 3d-1 done, brand-isolation tests pass. Tag `ai-phase-3`.

## Phase 4 — Operations agents (staff and admin)

> Check where the admin UI lives in your repo (client vs. `apps/staff`) before building the UI parts.

### 4a — Picker substitution
- **What:** when an item is out of stock during picking, suggests same-category alternatives with similar price.
- **Endpoint:** `POST /api/v1/ai/substitutions` (picker/staff roles).
- **Tools:** same-store, same-category, in-stock products.
- **Rule:** suggestion only; customer approval rules of your order flow stay unchanged.
- **Tests:** suggestions are in stock, same store; empty result handled.
- **Done when:** picker screen shows 2-3 valid alternatives.

### 4b — Admin triage (billing help + support)
- **What:** classifies `BillingHelpRequest` items (type, urgency) and drafts an answer.
- **Endpoint:** `POST /api/v1/ai/admin-triage` (admin only).
- **Tools:** the request itself, the brand's billing summary (read-only).
- **Rule:** admin approves every reply.
- **Tests:** non-admin 403; classification schema validated.
- **Done when:** each new help request shows a suggested category and draft in the admin view.

### 4c — Moderation agent
- **What:** scores a piece of text (review, product text, chat) for abuse/spam/scam and returns reasons.
- **Endpoint:** `POST /api/v1/ai/moderate` (internal + admin).
- **Output:** `{ score, labels[], reason }`; no automatic punishment.
- **Tests:** obvious abuse flagged; normal Roman Urdu text not flagged; injection text does not change the score.
- **Done when:** the admin "flagged content" view can call it on demand. (Phase 5a will call it automatically.)

**Gate 4:** staff/admin role tests pass. Tag `ai-phase-4`. **All agents are now built.**

## Phase 5 — Automation (agents running without a click)

Only start after Gate 4: automations reuse the agents.

### 5a — Event automations
- **New review** -> moderation agent (4c) -> if score high, hide into moderation queue; refresh the review-summary cache (1b).
- **New product / CSV import** -> suggest category + duplicate flag (3b).
- **Hook:** after the successful save in `review.controller.js`, product and `productCsv.controller.js`, **fire-and-forget** inside try/catch.
- **Done when:** a toxic test review lands in the queue and a failing AI provider does not break review posting.

### 5b — Scheduled automations (`jobs/aiJobs.js`)
- **Nightly:** low-stock forecast per brand -> notification via the existing notification service.
- **Weekly:** plain-language sales report per brand (data from analytics, text from AI).
- **Rules:** idempotent (store last-run), process brands in small batches with delays, skip brands with no activity.
- **Done when:** jobs run on schedule twice in a row without duplicate notifications.

### 5c — Risk and admin automations
- **Order placed** -> risk flags (very large COD, repeated cancellations) -> admin review list; **never auto-block**.
- **Billing help created** -> auto-run 4b classification.
- **Daily** -> admin activity digest.
- **Done when:** flags appear with reasons; nothing is blocked or punished automatically.

**Gate 5:** each automation can be switched off by an env flag; jobs verified idempotent. Tag `ai-phase-5`.

# 29 — AI Phase Roadmap (3 agents per phase: a / b / c)

> Place at `CityCart/docs/29-ai-phase-roadmap.md`.
> This file is the **build order**. It replaces section 7 of doc 27 and the phase columns in doc 27's tables.
> Architecture, guardrails and file layout stay in `27-ai-agents-and-automation-plan.md`. Vision details stay in `28-sightwise-integration.md`.

## How to work through it

1. Each phase contains **three** sub-phases (`1a`, `1b`, `1c`). Build and finish them **one at a time**: endpoint + tools + UI + tests, then move on.
2. One branch per sub-phase, for example `feature/ai-1a-listing-writer`, merged when its "Done when" is true.
3. A phase is **complete** only when its **gate** (below) passes. Then tag it (`ai-phase-1`) and start the next phase.
4. Order: **Phase 0 (foundation) -> Phases 1-4 (agents) -> Phase 5 (automation) -> Phase 6 (vision) -> Phase 7 (hardening)**.

## Overview

| Phase | Theme | a | b | c |
|---|---|---|---|---|
| 0 | Foundation | provider router | usage log + cache + kill switch | route, auth, rate limit |
| 1 | Quick-win generation | Listing writer (brand) | Review summarizer (customer) | Chat translator (customer + brand) |
| 2 | Customer assistants | Shopping assistant | Order helper | Service booking helper |
| 3 | Seller intelligence | Seller advisor (restock, pricing, analytics Q&A) | Catalogue matcher + CSV cleaner | Reply drafter (reviews + chat) |
| 4 | Operations agents | Picker substitution | Admin triage (billing help, support) | Moderation agent |
| 5 | **Automation** | Event automations (review, product) | Scheduled automations (nightly, weekly) | Risk and admin automations |
| 6 | **Vision link** (Sightwise) | "Scan product" in listing form | Fruit freshness scan | Return evidence + authenticity |
| 7 | Hardening | Security tests | Quota and cost review | Docs, release |

## Phase 1 — Quick-win generation (low risk, no tools, no data access)

### 1a — Listing writer (Brand)
- **What:** from a few words of notes, drafts title, description and a suggested category. Image input is deferred to the Phase 6 vision link.
- **Endpoint:** `POST /api/v1/ai/listing-draft` (role: BRAND_ADMIN or BRAND_EMPLOYEE). Body `{ notes }`, 3–400 characters.
- **Tools:** none. The server loads the active leaf categories itself, then validates the model output with zod `{ title, description, category }` and resolves the category against that list (`null` when it matches nothing). Nothing is written to the database.
- **UI:** "Draft the details for me" panel in the brand's **Request a new product** form on Add product (client). Brands do not author a listing's name, description or category directly — those come from the catalogue — so the request form is the only place a brand writes new product copy. On success the panel fills name, description and category; the brand edits them before sending the normal catalogue request. The panel is hidden when `AI_ENABLED` answers 503.
- **Tests:** zod validation (too short/too long); non-brand role gets 403 without a provider call; notes are sanitized; category resolved by id or name; unknown category returns `null`; malformed model output returns 502 `AI_BAD_OUTPUT`; provider failure returns 503; kill switch and daily limit return before any provider call; brand-employee membership path works.
- **Done when:** the button fills the form in a real brand account and the AI label is visible.

### 1b — Review summarizer (Customer-facing)
- **What:** 2-3 line summary of pros/cons for a product.
- **Endpoint:** `GET /api/v1/ai/products/:id/review-summary` (signed-in, any role). Guests keep the normal reviews and simply do not see the card.
- **Tools:** reads that product's approved reviews only (inside the service, no model-controlled IDs). The product must be public: active listing in an active brand. Review text is sanitized and marked as data in the prompt.
- **Cache:** `AiCache` keyed by product + approved review count for one hour; regenerate only when count changes. Minimum 3 approved reviews, below which the endpoint answers `summary: null` without a provider call.
- **UI:** "AI summary" card above the reviews grid on the product page (client). It is fetched only for signed-in users with 3+ reviews and disappears silently on a kill switch, quota or bad output. Shopper app is deferred with the "web first, apps later" decision.
- **Tests:** cache hit avoids a provider call; review text containing instructions is sanitized and never treated as instructions; below 3 reviews no provider call; a changed count regenerates; non-public product 404; malformed output 502; provider failure 503; kill switch and daily limit return before any provider call.
- **Done when:** summary appears, is cached, and refreshes after a new review.

### 1c — Chat translator (Customer + Brand)
- **What:** translates one chat message on request (Urdu / English / Roman Urdu).
- **Endpoint:** `POST /api/v1/ai/translate` with `{ messageId, targetLang }`; `targetLang` is `en`, `ur` or `roman-ur`.
- **Rule:** the caller never sends the text. The server loads the message and its conversation and checks the signed-in user is that conversation's customer or brand. The message body is sanitized and marked as data in the prompt; the model must answer `{ translation }`, validated with zod.
- **Roles and scope:** `CUSTOMER`, `BRAND_ADMIN`, `BRAND_EMPLOYEE` (employee needs `messages.view`), through `chatAccess`. Store chats only in this sub-phase; the direct provider and booking threads stay without Translate.
- **Cache:** `AiCache` keyed by `(messageId, lang)` for 7 days, because messages are immutable.
- **UI:** "Translate" action under a message bubble in the web ChatPanel (customer and brand dashboards). The picker offers English / اردو / Roman Urdu; the translation appears in an AI-labelled card **under** the original, which stays visible.
- **Tests:** non-participant gets 403; another brand gets 403; a non-chat role is refused before the message is loaded; invalid language 400; malformed id and missing message 404; cache hit avoids a provider call; cached by `(messageId, lang)`; injected instructions are stripped but the text survives; malformed output 502; provider failure 503; kill switch and daily limit return before any provider call.
- **Note:** a non-participant gets **403 `NOT_A_PARTICIPANT`** (the roadmap's required answer) rather than the chat service's deliberate 404 anti-probing answer. That is intentional for this endpoint and documented in docs/05 §23a.
- **Done when:** both sides can translate a message and the original stays visible.

**Gate 1:** 1a + 1b + 1c done, tests green, `AiUsage` reviewed (calls per agent, failure rate), kill switch tested again. Tag `ai-phase-1`.

## Phase 2 — Customer assistants (first use of tools)

Before 2a: build the **tool layer** (`tools/*.tool.js`, read-only, `(ctx, args)`) and the **agent loop** (max 3 steps, zod-validated tool calls). This is the main work of 2a.

### 2a — Shopping assistant
- **What:** "cheap rice near me", "gift under 3000", in Urdu / English / Roman Urdu.
- **Endpoint:** `POST /api/v1/ai/shop-assistant`.
- **Tools:** product search, categories, discover/nearby (existing services).
- **Output:** short answer + **product cards from real DB results**; the model may not invent products.
- **UI:** chat widget in the client and shopper app; tapping a card opens the normal product page.
- **Tests:** answers only reference returned product IDs; injection text in a product description is not obeyed; fallback to plain search on AI failure.
- **Done when:** five scripted queries return correct real products.

### 2b — Order helper
- **What:** "where is my order?", explains status, cancellation and return rules.
- **Endpoint:** `POST /api/v1/ai/order-helper`.
- **Tools:** the caller's own orders (`ctx.userId` only), return/cancel policy text from settings.
- **Rule:** can *suggest* **View order** and **Cancel order** buttons; the user performs the action on the normal order page. Cancel is offered only for an unpaid `PENDING` order, the rule the backend enforces. There is **no "Start return"** button: v2 has no customer-initiated return after delivery (docs/22 §F), so the answer explains the door-return rule instead.
- **Tests:** **user A can never read user B's order** (explicit test); unknown order returns a polite "not found".
- **Done when:** correct status answers for orders in each state.

### 2c — Service booking helper
- **What:** finds a suitable service provider and suggests a time slot.
- **Endpoint:** `POST /api/v1/ai/service-helper`.
- **Tools:** service discovery, categories, availability.
- **Rule:** only suggests; booking goes through the existing booking flow.
- **Tests:** suggested slots exist in availability data; no double-booking suggestions.
- **Done when:** a request like "AC repair tomorrow evening" returns real providers and slots.

### 2d — Recipe shopping list
- **What:** "chicken biryani for 6" -> the dish's ingredients, each matched to a real product nearby.
- **Endpoint:** `POST /api/v1/ai/recipe-list`.
- **Tools:** product search only (read-only).
- **Rule:** the model **extracts ingredients only**; matching is ordinary code over the same public product search the Stores page uses, so no product, price or shop can be invented. The list is a draft the customer edits; adding it to the cart goes through the normal cart API. Merged rows cannot add the same product twice.
- **Tests:** injected text is treated as data; unmatched ingredients stay honest ("Not found nearby"); provider failure degrades to a plain product search; extraction is cached, matching is live.
- **Done when:** a scripted recipe returns real products for most ingredients and the customer can add them to the cart in one click.

### 2e — Product comparison
- **What:** "compare two rice packs" -> a side-by-side table of real listings: price, stock, rating and the listing's own attributes.
- **Endpoint:** `POST /api/v1/ai/compare`.
- **Tools:** `compare_products { query, limit? }` — the same public product search the shopping assistant uses, enriched by ordinary code with up to 8 attribute pairs and approved-review ratings.
- **Rule:** the model **chooses which returned ids to show, at most 3**; every cell is read by the server from the listing, so no price, attribute or rating can be invented. The card is read-only; ordering happens on the normal product page. The product page's "Compare with similar products" button opens the panel with a prefilled question and never sends it.
- **UI:** **Compare** mode in the web `Ask CityCart` panel and a `CompareCard` table (attribute rows are the union of the shown products' keys, capped at 8).
- **Tests:** invented ids are dropped; strict tool arguments reject an ownership field; catalogue text stays data; the 3-step guard and provider failure both degrade to a plain product search; kill switch and non-customer role return before any provider call.
- **Done when:** a scripted comparison returns 2–3 real listings with attribute rows and the table renders in the panel.

### 2f — Chat reply draft (customer)
- **What:** a customer types what they want to say ("ask when they can come") and gets a ready-to-send message in the chat composer.
- **Endpoint:** `POST /api/v1/ai/chat-draft` with `{ kind, id, intent }`; `kind` is `provider` (direct chat) or `booking` (booking chat, `id` is the booking id). `intent` is 3–300 characters.
- **Rule:** the server loads the thread itself and checks the signed-in customer is its customer; another customer's thread is **404**. Only the last 8 messages reach the prompt, `SYSTEM` messages are dropped, attachments become `[sent a photo]`, and each message is cut to 500 characters and marked as data. A closed booking chat answers **409 `CHAT_NOT_OPEN`** before any provider call. The model answers `{ draft }` only (≤1000 characters) and nothing is written to the database.
- **Tools:** none; the endpoint reads the caller's own thread and calls the model once.
- **UI:** "Draft with AI" in the web `ChatPanel` composer on direct provider and booking threads; the draft fills the message box and is never auto-sent. Store chat keeps Translate and has no draft.
- **Tests:** non-customer role refused before the thread is loaded; another customer's provider and booking threads both 404; unknown or malformed id 404; closed booking 409; the prompt carries the provider name, recent history and intent in order and says the data is not instructions; injected text is sanitized; an empty thread is honest; malformed or oversize drafts 502; provider failure 503; kill switch and daily limit return before the thread is loaded.
- **Done when:** the button fills the composer in a real provider and booking thread and the customer can edit and send.

### 2g — One chat instead of mode buttons
- **What:** the customer no longer picks Find products / Compare / Cook / My orders / Services before typing. One `Ask CityCart` chat accepts any question and shows capability hints in the bot.
- **Endpoint:** `POST /api/v1/ai/chat` with `{ message, cityId?, lat?, lng?, lastMode? }`. `lastMode` is only a hint for short follow-ups and is validated; the server always routes.
- **Routing:** deterministic and testable (docs/05 "Unified customer chat"): order, then comparison, then recipe, then service, otherwise shopping. Greetings and `help` answer with hints and **do not** call a provider.
- **Rule:** the unified route calls the existing agents unchanged, so every card and every scope is still produced by the same read-only tools. The response adds `mode` and `hints`; the old per-agent endpoints stay available for the app and deep links.
- **UI:** the five mode pills are replaced by one hint list (Products, Orders, Services, Recipe list, Compare) and every example goes to `/ai/chat`. Answers are labelled with the mode that produced them; help answers render their hint chips. The product page's compare button only prefills the question.
- **Tests:** classifier cases in English, Urdu and Roman Urdu; precedence; follow-ups with `lastMode`; a client-sent mode cannot choose the agent; help spends no provider call; auth, role, validation, kill switch and daily-limit checks; duplicate product ids collapse; a tool+answer decision still runs the tool; service prices reach the model in rupees, not paisa.
- **Done when:** a mixed scripted conversation (product → order → service → recipe → compare) works in one thread with the right cards.

### 2h — Right answers, not confident guesses

- **What:** the customer questions the chat answered *something* instead of the true thing. Found by working through the whole customer question space the way a QA pass would — location, stock, money, orders, hours, distance, "how many", off-topic — in English, Urdu and Roman Urdu: `in which block did I set my location`, `show me all the stores that are in my block`, `do you deliver to DHA Phase 5`, `what is the delivery fee`, `are shops open now`, `where is my rider`, `which store is closest to me`, `kab tak ayega`, `who made you`. The sweep was then run a second time over the questions a shopper asks *after* those: the schedule (`what are your timings`, `do you work on eid`), the account (`where is my cart`, `forgot password`), the money words that are not money (`jazzcash`, `installment`, `my coupon is not working`), the paper and the phone (`bill chahiye`, `rider ka number`), working on the platform (`how do I sell my products`, `how to become a rider`), a delivery that went wrong (`wrong item delivered`, `saman kharab aaya hai`) and a booking the shopper wants moved (`cancel my booking`) — plus the thank you that used to be searched as a product name.
- **Location is resolved once, by the server:** `services/ai/location.js#resolveShopperScope` runs before any agent and its result travels down as `scope`, so no tool reads the request body again. Trust order: **a pin in this request → the customer's own default saved address → the `blockIds` the client says are selected → the city**. A malformed id or more than 10 of them is **400** before any read, agent or provider call; an id that turns out to be inactive, unknown or in a different city is simply **not trusted** — it is dropped and the answer falls back to the pin, the saved address or the city, because a hand-made list must never span the platform. Block names are never taken from the client's own words: they come from `activeBlocksContaining(lat, lng)`, the same rule the Stores page uses, so a redrawn zone changes the answer with nothing to update. `deliverable` is a tri-state: `null` ("no location was resolved") is a different sentence from `false` ("outside every published zone").
- **Tools:** `my_location` and `check_area` (`tools/location.tool.js`) read the shopper's own zone and any named zone from the block table. `search_products`, `find_stores` and `find_service_providers` all go through `inBlockThenCity` (`tools/area.js`): the shopper's blocks are searched first, the city is only a labelled second step, the count comes from `pagination.total` rather than the length of the page, and the "these are not from your block" warning is left in `ctx.scopeNote` so the answer the shopper reads carries it. `find_stores` keeps its `area` / `city` / `brand` scopes; the block scope is now the default when a block was resolved.
- **Three families answer with no model at all** (`services/ai/facts.js`), so a wrong one is not possible and the daily allowance is not spent: **location** (own block, a zone the shopper named, a CityCart city, a zone that has no shop yet, a name the platform never published); **policy** (delivery fee, COD-only payment, minimum order, delivery time, support contact, how to order, opening hours and days, the shopper's own account pages, the receipt, whose phone number may be shown, selling or riding on CityCart and what the checkout total is made of) — read from platform settings, from the routes and pages that actually exist and **from the rules checkout enforces**, which is why the COD order ceiling is deliberately *not* quoted: telling a customer a limit the backend ignores is its own wrong answer; and **off-topic**, which says what the chat can do instead of answering the question. A message with no searchable word (`fallbackQueries(text).length === 0`) asks for the item rather than paying for a search that returns random shops — and a message that is only a thank you or a goodbye is answered as one, because "tell me the item you want" after `shukriya` is its own small rudeness.
- **Routing** is now 11 checks in a fixed order — help, off-topic, order, policy, location, *mention-of-my-own-place*, compare, recipe, service, the last-agent follow-up, shopping — and the one decision a read has to settle happens after it: a SHOP message that names a real place **and** asks for shops (`shops in Karachi`) is answered by `answerLocation`, not by a product search for the word "Karachi", and a POLICY message that names a **real zone** while asking nothing the settings can answer (`do you deliver to DHA Phase 5 tonight`) is answered about that zone — `namedRulePlace` in `facts.js` decides, and it defers to the rules the moment the sentence asks about money, payment, hours, the account, a receipt or a number, because "the fee in DHA" is the same fee everywhere. `intent.js` also stopped treating filler as content: `my area` alone is the shopper's own block, `nearest` / `open` / `hours` / `refund` are rule words, and `rider`, `kab tak ayega` and `closest to me` belong to order and location, not to shopping. Words that are only politeness (`thanks`, `shukriya`, `khuda hafiz`) joined `query.js`'s stopwords so a thank you is never a search term, and `facts.js`'s `ROMAN_WORDS` joined them (`ka`, `ki`, `ko`, the Roman spellings of thanks and goodbye) because a sentence built out of those is Roman Urdu and an English reply to it reads as if the language was ignored.
- **Grounding covers the sentence, not only the cards** (`services/ai/ground.js`): every amount, percentage, distance, duration and rating the reply states is looked for in the numbers the tools actually returned — which is why `agentLoop` keeps `args` and `result` in the trace now. An unexplained number costs the sentence, not the answer: the real cards stay, the words become `serverSentence(mode, cards, scope)` written from them, and the block warning is appended either way. ObjectIds, urls and slugs are excluded from the evidence so two stray digits in an id cannot validate an invented price.
- **UI:** the drawer sends the blocks its Nearby list actually selected (`blockIds`) and the last `mode`, and labels the three new answer kinds (`location`, `policy`, `offTopic`) the same way it labels the agent modes.
- **Tests:** `tests/ai/intent.test.js` — the routing tables, one case per row of the matrix below, in all three languages, each family keeping its own guard rows (`wallet for men` is still a product, `order cold drinks` is still a purchase, `میرا پتہ کہاں ہے` is still a location question); `tests/ai/chatCorpus.test.js` — the real sentences, with the block names, zones, cities, coordinates and settings the shopper's own data provides, including "a shop that is not in your block is never called nearby", "a zone CityCart has never published is not answered with your own block" and "a zone answers a coverage question but never a money question"; `tests/ai/chat.test.js` — the server-answered families make **no** provider call and spend no allowance, and a `blockId` the shopper did not pick is rejected with 400 before any read. Every customer-agent suite stubs the scope through `tests/helpers/mockShopperScope.js`, so a suite cannot quietly hit the Block collection. `npx jest tests/ai` runs all of it: **37 suites, 2034 tests** (2026-11-25).
- **Done when:** the matrix below gives the listed answer for the seeded shopper, with no invented zone, fee, hour, distance or total, and the three server families cost zero provider calls.

#### Customer-question QA matrix (the chat's regression list)

Ask each one in the web `Ask CityCart` panel as the seeded customer, with the location the row says. Every row is a jest case; `npx jest tests/ai/intent.test.js tests/ai/chatCorpus.test.js tests/ai/chat.test.js` re-runs the whole matrix.

| Set location to | Customer asks | Answered by | Correct answer |
|---|---|---|---|

#### 3c-1 — the drafted reply answers from the shop's own records (2026-11-25)

The owner's report was one sentence: a customer writes *"tell me how many stock is available for this product"*, the shop presses **Draft a reply**, and the draft that comes back says nothing about stock. It was not a bad prompt — it was the design. The drafter was handed **no** facts at all (no price, no stock, no order status) on the reasoning that a model with no numbers cannot misquote one, so it could not answer either; every factual question got a polite paragraph. This is 2h's shape applied to the shop's side: **the server reads the record, the model only words it, and the finished sentence is checked before the shop sees it.**

- **`services/ai/brandChatFacts.js` — the reading half.** `familyOf(message)` routes the customer's newest message to one of ten families — `complaint`, `return`, `detail`, `rule`, `order`, `availability`, `timing`, `coverage`, `price`, `shopOnly` — in a fixed precedence (a fault word outranks a status word because the shop has to answer it; a rule word outranks an order word because "the minimum order" is CityCart's, not the customer's parcel) and in all three scripts, since `\b` is ASCII-only and a Roman Urdu sentence puts the unit *after* the number. Then only that family is read, keyed by the session's brand and by the customer named in the **conversation row** — never by anything the body sent: `Product` (by the listing the message was pinned to, or by the name in the sentence, scored both ways, and a tie is reported as a tie), `Inventory` (through `getInventoryForProduct` + `getStockStatus`), `Branch` → `Block` for the areas the shop's own branches stand in, `Brand.settings.estimatedDeliveryTime`, `Order` (this customer's open order first, else the last one), `Return`.
- **Two limits are existing rules, not new ones.** An exact quantity is read but is **never handed to the model** — `getPublicAvailability` already keeps the count off the customer's screens, so the reply states a *state* (`in stock`, `running low`, `out of stock`, `on our listing`) and the count comes back in `private.availableQuantity` for the shop's own panel beside it *(owner decision, 2026-11-25)*. And the shop's `deliveryFee`, `minimumOrderValue` and `operatingHours` settings are **not read at all**, because nothing in the code enforces them: checkout adds no fee and no minimum (`order.service.js`), no coupon entity exists, and no service reads the hours, so quoting them would have a shop promise money the platform does not handle *(owner decision: only enforced data)*. What CityCart does enforce is stated instead, in the shop's own voice, from the same facts the shopper's chat is given: no delivery fee, no minimum order, cash at the door, the receipt on the order's own page, no coupon codes.
- **`services/ai/draftGuard.js` — the verifying half.** Three things refuse a finished draft, and each refusal is replaced by a line **the server wrote from the records it read** (`serverDraft`), in the language the customer used: a money-or-parcel promise the platform cannot back (refund, replacement, re-delivery, reship, cancel, waive — in English, Roman Urdu and Urdu script, and the customer's own stored order state is *data*, so "your order was cancelled" stays allowed); any fee, minimum or coupon the platform does not enforce; and any figure the read records do not contain, including a bare stock count (`isGrounded(…, { counts: true })` — the count patterns are switched on **only** here, so the customer chat's grounding is untouched). The review half is guarded the same way with `{ rating, productName }` as its only evidence, and falls back to a thank-you line, never to a promise.
- **Three answers, and the client says which one it got.** `source: 'model'` is the shop's own words (`grounded: true`) or those words replaced (`corrected: true`, with `reasons`); `source: 'server'` means **no provider call was made at all** — a platform rule, a listing the customer did not name ("Which item do you mean — Basmati Rice 1kg, Basmati Rice 5kg?"), an order that does not exist — so these cost no daily allowance, the same win 2h gave the shopper's chat; `source: 'none'` means CityCart holds nothing that answers, and the shop gets `draft: null` plus a `note` naming the screen that would fix it (`Shop → Settings` for a timeframe, `Shop → Branches` for areas, opening hours and contact details are said to be the shop's own to answer). `client/src/components/chat/ChatPanel.jsx` shows that note, the private count and the correction under **Draft a reply**; `client/src/pages/brand/Reviews.jsx` shows the correction under **Draft with AI**.
- **Still no write path, and nothing new leaves the server.** The endpoint is `POST /api/v1/ai/reply-draft` with `{ type, id }` and the same two permissions as the screens it answers for (`products.view` / `messages.manage`); the ids of the listing, the order, the return and the branch, the customer's e-mail and phone and the order's own number are read but never sent to a provider, and an invented rupee in the model's answer is caught before the shop sees it.
- **The drafted-reply QA matrix.** Ask each line as the customer in a seeded thread, then press **Draft a reply** as the shop. Ask the same sentence in Urdu and Roman Urdu: the reply comes back in the language the customer wrote, because the *customer's* text sets the language of the line the shop is handed.

### 3e — Returns reason clusterer (the first of 3d, built in the first half)
- **What:** the brand asks why orders come back and gets the real reasons, grouped, with counts and the products they cluster on, plus the rupee value of what came back.
- **Endpoint:** `POST /api/v1/ai/returns-insights` (brand roles, `delivery.view` + `requireTenant` — the same guards as `GET /returns`, because it answers the same inbox).
- **Tools:** this brand's `Return` rows only — the four stored reason enums, the per-line `productName`, `quantity`, `restock`, and `returnedSubtotal` / `refundAmount` / `feeRefunded` — plus the delivered order and listing behind them. Counts, percentages and totals are computed in code; the reason enum is never free text, so a theme is always one of the four.
- **UI:** a panel on the brand Returns page for the whole shop, and on `ReturnDetail.jsx` a drafted dispute/decision reply for that one return — copy only, since the store's real action stays the ordinary **Mark received** / restock-decision buttons.

### 3j — Bill explainer (the sixth of 3d)
- **What:** the shop opens one of its own invoices and asks why the bill is this size, and gets the five stored amounts, the largest commission lines that built them with the order each was charged on, the refunds reversed off the bill, the payments submitted against it, four comparisons of one stored record against another, and one plain-language paragraph saying how they fit together.
- **Endpoint:** `POST /api/v1/ai/billing-explain` (brand admin + `requireTenant` — the same session-derived tenant `GET /billing/invoices/:id` already requires; there is no permission gate on the billing surface itself to reuse). Only `{ invoiceId }` may be sent and it must be a 24-hex id: no window, no brand, no amount, no rate.
- **Tools:** four reads, all of them scoped in the query. `SellerInvoice.findOne({ _id, sellerType: 'BRAND', sellerId: brandId })`, then `CommissionEntry.find({ invoiceId })` sorted as the invoice screen sorts it, `SellerPaymentClaim.find({ invoiceId, … })` for what was submitted, `SellerPaymentClaim.find({ creditAppliedInvoiceId, … })` for what an earlier overpayment carried in, and one bounded `Order.find({ _id: { $in: … }, brandId })` for **only** the orders behind the lines the panel actually prints. Photo-free, customer-free: names, addresses, phones, items, `reference`, `receipt`, `verifiedBy` and `rejectionReason` are dropped before anything is compared.
- **UI:** the **AI bill read** card inside the invoice detail modal on `pages/billing/Billing.jsx` (`components/brand/BillingExplain.jsx`) — the four amount tiles, the paragraph, the four comparison rows with their holds / does-not-hold / cannot-be-checked verdict, the line rows with each order's own figures and the model's note under a line, the payment chips grouped by status, and a footer that prints the period, due date and status sentences. - **Rule:** CityCart has **no payouts**, so the money a shop asks about is the bill it *owes*, and every rupee answering that is already on a record. `billingExplain.rules.js` adds stored fields together and compares stored fields to each other — `commissionForPaisa` is never imported, the 1% is never re-derived, and nothing here works out what a charge *should* have been. Where two records disagree the answer says they disagree and points at the Help tab, because deciding which record is right is the platform team's job (docs/15 §20.8). - **Tests:** `tests/ai/billingExplain.test.js`, 157 cases — another shop's invoice id and a non-existent one 404 identically; a body with any extra key, a non-hex id or a missing id is refused before a read; the answer's amounts equal the invoice's fields and the sums of its own lines; each of the four comparisons is checked in both directions and the paragraph of a failing month names the Help tab; an order belonging to a second brand is never fetched even when a foreign `sourceId` is planted in a line; a `customerId`, phone, address, IBAN, receipt or reference is absent from the whole payload and from the provider body; a line whose order came back part-collected is printed side by side, never as a mismatch; a `DRAFT` or `VOID` invoice, a `SERVICE_BOOKING` line and an unknown status are described truthfully instead of guessed at; an invented or off-table note id is dropped; the kill switch and the daily limit answer before any record is read; no write method on `SellerInvoice`, `CommissionEntry`, `SellerPaymentClaim` or `Order` is ever called.

- **Done when:** a scripted month answers with the amounts, the lines, the payments and the four verdicts the records themselves support, and the same figures appear with the provider switched off.
- **Status:** built on `new` (2026-11-22). **Renamed from "COD payout explainer" / `payout-explain`:** docs/15 §1-§2 establish that the platform never holds a shop's COD cash and issues no payout record, so a `payout-explain` endpoint would have had nothing to read. The feature answers the question the records can actually answer, and the backlog row above keeps the original wording so the change of name stays visible.
- **What is still not built, and why:** nothing is claimed about *whether the charge is right*. `SellerInvoice` and `CommissionEntry` are immutable history and `generateMonthlyInvoices` is the only thing that decides an amount; a panel that agreed with the shop's own records would still be second-guessing the ledger, so the model is told not to call a bill fair, wrong, high or low, and the four comparisons only ever report agreement or disagreement between stored fields.

### 3k — Deadstock re-pricing (the seventh of 3d)
- **What:** the shop picks a window — 30, 60 or 90 days — and gets the live listings on its own shelf that sold nothing in it, how long each has waited since it last sold, what a bounded markdown would take off it, what the unsold units are worth today and what the shop gives up if every one of them sells at the suggested price.
- **Endpoint:** `POST /api/v1/ai/deadstock-pricing` (brand roles, `products.view` + `requireTenant` — the same guard as `GET /products/mine`, because this is the product list read a different way). Only `{ days }` may be sent: an integer 30–90, default 30, clamped in code as well as refused by zod. No brand, no product ids, no date range, no price and no percentage may be sent — a shop cannot aim the read at someone else's shelf or talk it into a deeper cut.
- **Tools:** three reads, each locked to `ctx.brandId` inside its own query. `Inventory.find({ brandId, quantity: { $gt: 0 } }).sort({ quantity: -1 }).limit(240)` selecting `productId quantity reservedQuantity trackInventory`; `Product.find({ _id: { $in: those ids }, brandId })` selecting `name sku price compareAtPrice status isActive`; and **one** `Order.aggregate` over the shop's own `DELIVERED` orders for the 365 days behind the window, restricted to exactly those listing ids, which measures two things in the same walk — units sold inside the window and the last date anything sold. Names, SKUs and prices are sanitised before they reach a prompt; no `customerId`, order number or address is read at all.
- **UI:** the **AI price read** panel at the foot of `pages/brand/Products.jsx` (`components/brand/DeadstockPricing.jsx`) — window chips, the four tiles (sitting listings and units, worth today, given a price, less if all clear), the ladder and margin sentence, the paragraph, then one row per listing with `PKR 1,500.00 → PKR 1,275.00` struck through, the days it has waited, what the shelf is worth at both prices, the clamp sentence when the shop's own lower figure stopped the ladder, the model's note, and `Open this listing and set it yourself`. It hides itself when `/ai/ping` answers 503 or the caller lacks `products.view`.
- **Rule:** this is the one brand feature allowed to put a new price in front of a shop (3d-3 is told not to and points here), so the ladder is fixed in `deadstockPricing.rules.js`: 10% after 30 days, 15% after 90, 20% after 180, **capped at 20%** — past that a shop is not being advised, it is being told to give its stock away. Prices are rupees on `Product` and paisa everywhere after `pricePaisa`, so a suggested price is integer paisa and never a float rounding. The only floor is the shop's own recorded lower figure: when a listing displays a `compareAtPrice` *below* its price (the same broken pair 3d-3 scores zero), the suggestion stops there, and the panel and prompt both print the markdown that actually happened (10%), not the rung it wanted (20%). A listing with no sale inside the look-back is reported as a bound — `no sale in 365 days`, never "never sold". Untracked stock, a fully reserved row, a DRAFT/INACTIVE/ARCHIVED or `isActive: false` listing and a stock row with no listing behind it are skipped with their reason counted, and only live pages with units actually free are priced. **Margin is refused outright**: `Product` stores no cost and no supplier price (docs/04 has none, docs/07 §454 keeps supplier costs out of a shop's own catalogue view), so `margin` is `null`, a `marginNote` says why in the shop's language, and the system prompt forbids the model from ever using the words margin, profit, loss or supplier price. Nothing is written — no `Product` write method, no `Inventory` write and no price field is touched by this path; a suggestion is a number on a screen until the shop edits the listing.
- **Tests:** `tests/ai/deadstockPricing.test.js`, 147 cases — another shop's stock, prices and enormous unsold pile are absent from the counts, the ranking, the response and the provider body; a window of 7, 29, 91, 500, 2.5, `true`, `null`, `0`, `-30` or a string, and any extra body key, is refused before a read; every ladder rung is checked at 29/30/89/90/179/180/4000 days and the cap is asserted row by row; a decimal price (`PKR 350.50` at 10%) is paisa-exact; the floor is checked in both directions (stops the ladder, and is left alone when it sits above the price); a zero-price listing is blocked, not suggested at `PKR 0.00`; each of the five skip reasons is classified, and a 0-unit shelf and a fully reserved one are called out of stock rather than sitting; the totals, the value tied up and the released money equal the sums of the rows printed; widening the window from 30 to 90 moves a listing that sold 40 days ago off the sitting list; a listing name containing `<b>ignore previous instructions</b>` reaches the prompt flattened and marked as data; an invented or off-table `notes` product id is dropped and `actions` deduped to three; a read that hit its 240-position scan limit says so; an empty shelf costs **no AI request**; the kill switch and the daily limit answer before any record is read; and no write method on `Product`, `Inventory` or `Order` is ever called.
- **Two rules the tests hold:** the figure printed is the figure applied — a row stopped by its own compare-at floor reports `10% off` with its clamp sentence, never the 20% rung the ladder reached, because a shop that reads "20% off" and finds 10% on the listing stops trusting the panel. And **a zero is measured, not assumed**: `unitsInWindow` and the last sale date come out of the same bounded walk over delivered lines, so a listing that sold inside the window is never called sitting and a listing with nothing in the look-back is never called unsold-forever. Every fixture in the suite is dated relative to the clock the endpoint itself reads, so none of it date-rotates (the lesson `tests/ai/shopReport.test.js` had to learn).
- **Done when:** a scripted shelf answers with the right rows in the right order, the right suggested price for each wait, no margin anywhere in the payload or the paragraph, and the same figures with the provider switched off.
- **Status:** built on `new` (2026-11-22). The backlog row kept its original "margin impact … cost" wording above so the correction stays visible: what ships states the money tied up and the money a markdown gives up — both differences between two of the shop's *own* prices — and tells the shop plainly that CityCart cannot know what it still earns after the cut, because it was never told what anything cost.

The route is `authenticate` + `requireRole(SUPER_ADMIN)` + kill switch + daily limit. Type is rules-first and the model may only rename it inside the fixed list; urgency is `max(rules, model)`; a draft that invents a `PKR` amount, links out or promises an approval is replaced with the rules draft, and the same rules draft is the degraded answer. The admin web's Help tab shows **Suggest a category and reply** in the answer dialog (`client/src/components/admin/HelpTriage.jsx`); **Use this draft** fills the ordinary answer box and nothing is sent until the administrator presses **Send answer**. `tests/ai/adminTriage.test.js` covers 19 cases: rules, route authorization, seller scoping, prompt data markings, the draft guard, the urgency floor, the service-provider path, degraded output, the kill switch, the daily limit and no writes.

### 4c — Moderation agent
- **What:** scores a piece of text (review, product text, chat) for abuse/spam/scam and returns reasons.
- **Endpoint:** `POST /api/v1/ai/moderate` (internal + admin).
- **Output:** `{ score, labels[], reason }`; no automatic punishment.
- **Tests:** obvious abuse flagged; normal Roman Urdu text not flagged; injection text does not change the score.
- **Done when:** the admin "flagged content" view can call it on demand. (Phase 5a will call it automatically.)
- **Status:** built (2026-11-23). `moderation.rules.js` owns the score: fixed whole-word and pattern lists for insults, threats, spam and scam/private-detail wording (English and Roman Urdu) plus URLs, emails and Pakistani phone numbers, with `FLAGGED` ≥ 60, `REVIEW` ≥ 30 and `CLEAR` below. Text is scored by the server, so an injection cannot move the number, and the model is only asked for a one-sentence reason (guarded against link/action claims) in `moderation.prompt.js` + `moderation.agent.js`. The body is `{text}` only — no review id — so the check cannot reach a record; no record is read or written, and the only write is the caller's `AiUsage` row. The route is `requireAdminPermission(admin.reviews)`, the same door as the admin reviews list, so a read-only partner is refused. `client/src/components/admin/ReviewCheck.jsx` adds **Check wording** to each review on the admin Reviews page; it shows the score, verdict, labels and reason and never hides anything. `tests/ai/moderation.test.js` covers the flags, the Roman Urdu and English clear cases, the whole-word boundary, the injection-invariance case, route authorization (including partner permission and read-only), strict validation, the model reason guard, degraded output and no writes.

**Gate 4:** staff/admin role tests pass. Tag `ai-phase-4`. **All agents are now built.**

### 0b. Make every AI feature answer: `npm run seed:ai`

A realistic shop is not automatically a *complete* one. Several agents only speak when the data
has a specific shape — the review summary needs three approved reviews on **one** listing, the
substitution agent needs an order a picker is standing at with a line that has no stock, the
delivery promise needs a timeframe written in the brand's settings. `scripts/seedAiFixtures.js`
reads the database as it stands and adds only what is missing, so no endpoint answers "not enough
data" during a demo.

It is a top-up, not a reseed: run it against a database that already holds your data, as many
times as you like, and it stops as soon as nothing is missing.

```bash
cd server
npm run seed:ai                  read-only: prints a ready / needs table, writes nothing
npm run seed:ai -- --apply       adds the missing rows
npm run seed:ai -- --undo        deletes exactly the rows --apply wrote
npm run seed:ai -- --brand="Loom"  choose the tenant (default: the busiest ACTIVE brand)
npm run seed:ai -- --images --apply  repoint only the photos whose Cloudinary link answers 404
```

It never drops a database and never deletes a row it did not create: every id it writes is
recorded in `server/scripts/demo/.ai-fixtures.json` (gitignored), which is what `--undo` reads.
Two things are edited rather than created, so `--undo` leaves them in place — a brand's **blank**
delivery promise (it writes `"2-3 days"` only when the current text cannot be parsed as a
timeframe) and a service provider's working windows — and both are ordinary settings you can
change in the UI afterwards. Every fixture is dated from the day it is written, so the
7/30/90-day windows keep finding it; every name and note carries the mark `AI demo`, so it is
recognisable in the UI.

**Photos.** Ten listings are photographed for real. `seed:demo` uploads the folders under the
repository's `Images/` directory to Cloudinary (into `citycart/demo/<folder>`, with the links
remembered in `server/scripts/demo/.image-cache.json` so seeding twice does not upload twice) and
gives those listings a gallery of their own photographs: the bedsheet, knife set, oven mitt,
defrosting tray, kitchen towels and journal at Sukoon Home, the running shoes and travel backpack at
Zaitoon Footwear, the GPS watch at Mehr Menswear, the USB-C cable at Gulberg Gadgets. Everything the
camera does not have — cloth, jewellery, kurtas — and every fixture in the table below keeps a
placeholder link (`picsum.photos`, or `loremflickr.com` with `SEED_IMAGES=keyword`). A missing
`Images/` folder, a missing Cloudinary key or `SEED_IMAGES` is not an error: the seed prints which
photos it skipped and seeds links instead, so nothing here depends on media being uploaded.

`--images --apply` rewrites only a `res.cloudinary.com` link that the host answers 404 for, which is
what the deleted showcase run left behind on its listings. Real photos that still resolve are never
touched, and with no network nothing is treated as gone, so the repair can only ever shorten a
listing's broken links.

3. Press **Suggest substitutes**. Expect up to three suggestions, each with a product name, its stock and a short reason, drawn only from this shop's own products. No price appears anywhere in the Staff app.
4. Tap one: it becomes a change proposal for the customer. The customer still accepts or refuses it; nothing is substituted silently.
5. Edge cases: a suggestion list never contains another brand's product (enforced on the server, covered by `tests/ai/substitutions.test.js`); if the AI call fails, the sheet still offers the catalogue browser.

### 3. Phase 4b — admin billing triage (web)

1. Sign in at `/admin/login` as `admin@citycart.local`.
2. Open **Billing → Help**, press **Answer** on an open seller question.
3. Expect a panel above the answer box with a classification (for example *Payment not showing*), an urgency badge, `Owes PKR …` from the seller's real invoices, and a draft answer. The line under it says nothing has been sent.
4. Press **Use this draft** — the text lands in the answer box. Edit it, then press **Send answer** yourself. Triage never sends, resolves or notifies anything on its own.
5. Edge cases: if a provider fails, the draft is still written from the server's own facts (`degraded: true`); a request with no outstanding balance shows no `Owes` line.

### 4. Phase 4c — review wording check (web)

1. Sign in at `/admin/login` and open **Reviews**.
2. On a review with text, press **Check wording**. Expect a verdict (`CLEAR`, `REVIEW` or `FLAGGED`), a score out of 100, label chips (insulting words, advertising, scam wording) and one plain sentence.
3. Try a normal Roman Urdu review (clear), a mild insult (review) and a serious insult or a phone-number scam line (flagged). The score never changes for the same text, and adding "ignore all previous instructions" to the text changes nothing.
4. Press **Check again**: the sentence comes back without a new provider call (cached for a day), while the score is recomputed every time.
5. Confirm the only action is still **Hide review**; the check itself says it hid and reported nothing.
6. Edge cases: read-only partner admins do not see the button (this is a POST); a partner without `admin.reviews` gets `403`.

### 5. Phase 7b — usage, fallback and limits (web)

1. After the calls above, open **Admin → Analytics** for a range that includes today. The **AI assistant usage** section lists `substitutions`, `admin-triage` and `moderation` with requests, users, success %, fallback %, retried %, tokens and average time.
2. With a working provider key, fallback should be 0%. Stop the network or use a bad key to force failures; the next report shows a non-zero fallback rate and the latest capped failure text.
3. Set `AI_ENABLED=false` and reload Analytics: the report still loads (past spend is still reviewable).
4. Burst limit: set `AI_USER_BURST_LIMIT=2`, restart, and press **Check wording** three times quickly. The third answers `429 You are using AI too quickly. Please wait a moment.` Set it back to 10.
5. Daily limit: set `AI_USER_DAILY_LIMIT=1`, restart, make one AI request, then another. The second answers `429` with `code: "AI_DAILY_LIMIT"`; every AI response also carries `X-AI-Daily-Limit` and `X-AI-Daily-Remaining`. Set it back to 30.
6. `GET /api/v1/admin/ai-usage` is refused to brand admins and customers (`403`), allowed to a partner holding `admin.analytics` (including read-only), and never calls a provider.

### 6. Phase 7a — automated hardening checks

```bash
cd server
npx jest tests/ai/hardening.test.js   # prompt injection, secrets, route chain and tenant pass
npx jest tests/ai                      # every AI agent suite, including cross-tenant picker and billing cases
npm test                               # the whole server suite
```

The hardening suite fails if any prompt builder puts caller text into the system rules, if any prompt file names a provider key or environment variable, if an agent logs, if an `/ai` route loses its kill switch, limiter or daily allowance, or if the controller takes an owner id from the body.
